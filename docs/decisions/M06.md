# M06 scheduler and scale decisions

## Scheduler and budgets

- Input rows are parsed and checkpoint shells are created before network work. Unique organisation numbers receive one official BRREG action, with a maximum of four official workers. Duplicate input rows retain separate terminal envelopes and share the exact-organisation result.
- The scheduler completes the `official_foundation` pass before it can dispatch optional `website_verify` actions. Candidate work is scored with the audited formula: `4 × expected company-family gain + expected atomic-claim gain − 8 × identity risk − expected requests − 0.2 × expected seconds − 10 × expected paid cost`. Scores only order permitted work; they do not change evidence or publication rules.
- Expected website gain uses M05 measurements (1/200 accepted exact sites, zero verified job/activity claims; 96 physical and 152 logical requests). Website work remains enabled at low priority and is not permanently disabled.
- M02 measured 402 physical requests / 100 companies and about 288.8 seconds. M06 uses 4.02 expected official requests and 2.888 expected seconds per company for scheduling.
- Default local fallback limits remain 1,800 seconds hard, 1,350 seconds soft, 300 seconds completion reserve, `12N+1000` physical requests, $0 paid cost, 32 global HTTP concurrency, 2 per-host concurrency, BRREG 3 requests/second, and 4 concurrent official company actions. Configured logical-request limits are enforced when supplied; no new Builderr logical limit is assumed.
- Per-company and per-host physical request caps are configurable and enforced atomically when supplied. The audited plan gives no fallback numeric caps, so both remain unset unless the runtime configuration or environment provides them. Observed per-company/per-host totals remain in run accounting.
- Optional website actions stop at the soft deadline, completion reserve, or exhausted physical/logical request capacity. Required official work can continue after the soft deadline and stops at the completion reserve. Every physical attempt, logical call, retry, redirect, cancellation, and coalesced request remains separately accounted.
- A 429/503 applies the advertised `Retry-After`, halves the host rate, and halves host concurrency (minimum 1). The limiter recovers one step after five successful responses.
- Identical in-flight GETs coalesce only when their URL, purpose, user agent, response cap, robots policy, allowlist, and access profile match. Each caller increments logical accounting; the transport attempt is counted once. Response interpretation and identity proof remain per caller. No persisted response cache was added.
- SQLite WAL/FULL checkpoints track `pending`, `baseline_done`, and `terminalized`; one queue writer serializes per-company updates during the concurrent official pass, and the run loop serializes terminalization afterward. Resume fingerprints the input, snapshot, configuration, prior state, cutoff, and budget. JSONL publication still uses a single sorted atomic writer and verifies exact input row cardinality before replacement.
- Search, ATS providers, external activity providers, browser actions, models, paid APIs, and other unpromoted integrations remain disabled. Their zero-cost/no-provider fallback is unchanged.

## M06 scale results

See [m06-scale-benchmark.json](../audit/m06-scale-benchmark.json) for the run-level measurements. The required synthetic 1,000-company simulation terminalized 1,000 official foundations and produced 1,000 ordered outputs in 3.575 seconds; the 1,200-company simulation terminalized 1,200 and produced 1,200 outputs in 4.577 seconds. Both had zero official starvation, zero wrong-company promotions, global concurrency capped at 8, and per-host concurrency capped at 2. Their modeled physical/logical requests were 4,500/4,780 and 5,400/5,736 respectively; in-flight coalescing accounted for 280 and 336 logical calls. These are deterministic scheduler simulations, not live elapsed-time estimates. Offline operational CLI/checkpoint/output runs produced available, ordered envelopes at 1,000, 1,200, and 10,000 rows with zero network requests. Runtime and peak traced/RSS memory were 2.990 sec and 11.07/62.40 MiB; 3.646 sec and 13.10/73.71 MiB; and 28.409 sec and 110.27/231.56 MiB respectively.

Stress modes A/B/C/D all fit the simulated workloads. The additional 1,000-company budget-pressure case reserved the 4,020-logical-request official foundation first, deferred 480 optional website actions, retained all 1,000 official terminal results, and used no paid services.

The final 100-company live BRREG sample produced 100 exact identity anchors and 100 terminal envelopes, with zero wrong-organisation claims or row errors. It used 402 physical requests (100 each for entity, accounts, roles and subunits, plus two robots attempts) and 401 logical calls. Runtime was 316.509 seconds with 0.778 seconds finalization and 1,483.491 seconds left before the hard deadline; each company used four physical requests. The two robots attempts ended as one transport error and one timeout. The structured BRREG API continued under the already accepted M02 policy for robots transport outages; ordinary website robots enforcement remains unchanged. Exact output checks and run metrics are recorded in the benchmark report.
